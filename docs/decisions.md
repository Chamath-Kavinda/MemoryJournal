# Decisions

Choices the build documentation left open, recorded as the documentation requires.

## D-001: TypeScript is pinned to 6.0.x

The documentation asks for the latest stable versions. The latest TypeScript (7.0) is not yet supported by `typescript-eslint` (supported range is `>=4.8.4 <6.1.0`), which would leave ESLint running against an unsupported compiler. TypeScript is pinned to `~6.0.3`, the newest version in the supported range. Revisit when `typescript-eslint` adds TypeScript 7 support.

## D-002: Line endings are LF everywhere

Development happens on Windows, where Git defaults to CRLF. `.gitattributes` (`* text=auto eol=lf`), `.editorconfig` and Prettier (`endOfLine: lf`) all enforce LF so diffs and hooks behave the same on every machine.

## D-003: Core package is consumed as TypeScript source

`packages/core` exposes `src/index.ts` directly (no build step). Expo, Metro and Electron's bundler all compile workspace TypeScript, so this avoids maintaining a separate build output for the package.

## D-004: Timestamps in core are epoch milliseconds

Domain types in `packages/core` use epoch milliseconds (UTC) for every timestamp instead of Firestore `Timestamp` objects. This keeps core free of Firebase dependencies and trivially testable. Platform adapters convert at the Firestore boundary.

## D-005: Dependency build scripts are allow-listed

pnpm blocks dependency install scripts by default. Only `@swc/core` (used by the Jest transform) is allowed in `allowBuilds` in `pnpm-workspace.yaml`. New entries need a reason recorded here.

## D-006: Revision and sitting rules the documentation left open

- A new sitting always creates the next revision, even on the same calendar day. Revisions are immutable once a sitting ends, so the documentation's later save session on any later day is applied to every new sitting.
- The last activity of a sitting is the day document's `updatedAt`; if unknown, the open revision's `createdAt` is used.
- `addedWordCount` compares against the previous revision as a multiset of words, ignoring case and surrounding punctuation. Revision 1 has no previous pass, so all of its words count as added.
- Library item revisions (section 5.5) have no `closedAt` in the data model, so their helper is added together with the library feature.

## D-007: Firebase runs on a demo project until a real one exists

The emulators and the rules tests use the project ID `demo-memory-journal`. The `demo-` prefix tells the Firebase CLI to run fully offline, so no Firebase project, login or billing is needed to develop or test. A real project ID and its web config go into `apps/app/.env` (see `apps/app/.env.example`) before the first real sign-in.

`firebase-tools` is a pinned root dev dependency, set to `14.27.0` instead of the latest 15.x. Version 15 refuses to run the emulators on Java before 21, and the machine in use has Temurin 17. Move to 15.x after installing JDK 21 or newer.

## D-008: protobufjs install script stays blocked

`firebase-tools` pulls in `protobufjs`, whose install script only prepares its optional CLI. It is set to `false` in `allowBuilds` (see D-005).

## D-009: Closed revisions can only be deleted during account deletion

Section 7.1 makes closed revisions undeletable, but section 5.9 requires "delete account and all data", and v1 has no Cloud Functions to do that from a server. The account deletion flow first sets `deletionRequestedAt` on `users/{uid}`; while that field exists the owner may delete closed revisions. Everywhere else a closed revision is read-only. A user can only ever use this on their own data.

## D-010: Rules tests use the real clock and pinned test libraries

The Firestore emulator evaluates `request.time` with the real clock, which cannot be mocked. The rules tests therefore pick a stored `utcOffsetMinutes` that puts local time about 20:30 or 21:30 right now, never exactly at 21:00. The exact 20:59 and 21:00 boundary is covered by the unit tests in `packages/core`.

The tests use `@firebase/rules-unit-testing` 5.0.2 with `firebase` 12.19.0. Version 6 of the test library needs Node 24.12 or newer, while CI runs Node 22. The `@firebase/util` install script is blocked in `allowBuilds` (see D-005) because it is not needed. CI installs Temurin 17 for the emulator.

## D-011: The stored UTC offset is client-reported

The rules trust `utcOffsetMinutes` from the user document, because the server has no other way to know the user's zone. It is limited to real offsets (-12:00 to +14:00, steps of 15 minutes). A user could still set a false offset to unlock today early. That only affects their own private journal, so it is accepted for v1. Changing the device clock alone does not help, because the rules use server time.

## D-012: The app runs against emulators until a real Firebase project exists

The local .env (git-ignored) holds placeholder Firebase and Google values with EXPO_PUBLIC_USE_EMULATORS=true, so the app starts without a real project. Real sign-in needs a Firebase project and a Google OAuth web client ID. Replace the placeholders and set the flag to false. Android emulators reach the PC at 10.0.2.2, so set EXPO_PUBLIC_EMULATOR_HOST to that (or the PC's LAN IP for a real phone).

firebase/auth exports getReactNativePersistence only under the React Native bundle condition, so its types do not declare it. apps/app/src/types/firebase-auth-rn.d.ts declares it. The web build has a placeholder sign-in that is replaced by the browser-based flow in the Electron commit.

## D-013: Desktop Google sign-in uses PKCE in the system browser

The Electron main process starts a loopback server on 127.0.0.1 (random port), opens the system browser to Google, checks the state value, and exchanges the code for an ID token with a PKCE verifier. The ID token goes to the renderer through the preload bridge and is passed to Firebase with signInWithCredential. This needs a separate Google OAuth client of type Desktop app, read from MJ_GOOGLE_DESKTOP_CLIENT_ID and MJ_GOOGLE_DESKTOP_CLIENT_SECRET (Google does not treat a desktop client secret as confidential). The Expo web export is served through a custom app:// protocol because file:// breaks its absolute asset paths. The tray and 9 PM scheduler stay in commit 36.

## D-014: The profile is created on first sign-in and its time zone is refreshed on foreground

users/{uid} is created the first time a signed-in user opens the app, with stats at zero, the reminder on and the theme set to system. The stored time zone and UTC offset are compared with the device on every sign-in and whenever the app returns to the foreground, and only changed fields are written. This keeps the offset right across travel and daylight saving changes, which matters because the Firestore rules use it for the 21:00 unlock. If Firestore is unreachable the sync is skipped and retried on the next start or foreground.

## D-015: The home calendar shows written days for one month and starts weeks on Monday

The calendar listens to users/{uid}/days for the visible month only (date range query on the date field, no extra index) and marks a day as written when its wordCount is above zero. Weeks start on Monday; core supports Sunday if a setting is added later. Next month is blocked past the current month and future days are disabled. Today comes from the device clock for display only. The streak and score top bar and the bottom or side navigation are not built here because there is no streak or score data until Milestone 5; tapping a day is wired to the Day screen in commit 18.

## D-016: The Day screen gets server time by stamping the user document

The lock state uses the stored utcOffsetMinutes plus the device clock moved onto Firestore server time. The app writes clockProbeAt: serverTimestamp() to users/{uid}, reads it back from the server and takes the midpoint of the round trip as the clock offset, on opening a day and when the app returns to the foreground. Without Cloud Functions this is the only way to get server time. When offline the last known offset (zero at start) is used; the Firestore rules still decide every write. The Day screen shows the date, a status banner with a countdown to 21:00 for today and a plain message for future days. The writer itself arrives in commits 19 to 23.

## D-017: Hourly rows edit a draft held in memory, one row open at a time

The Day screen shows the Free Notes block and 24 hourly rows. Rows are collapsed with a one-line preview and only one row is open at a time. The draft is a DayContent from packages/core, and an empty row removes its block so empty rows are never stored. Opening a row edits only the whole-hour text; minute markers arrive in commit 20. While today is locked nothing can be typed, and only rows that already have text can be opened to read. The draft is not saved anywhere yet: autosave is commit 21 and saving revisions is commit 22.

## D-018: Minute markers are separate blocks, added by minute at the cursor

Inside an open hourly row, Add minute asks for a minute (0 to 59, with or without a leading colon) and inserts a marker for it. The marker is a block with that minute, as the data model requires. The documentation says the marker goes at the cursor, and a plain text field cannot hold an inline marker, so the cursor splits the text: what comes before stays where it was and what comes after moves into the new marker, with whitespace at the cut trimmed. The cursor can be in the whole-hour text or in another marker. If the cursor is unknown, the marker starts empty. A minute that already has a marker is refused with a message instead of merged. Remove deletes a marker and appends its text to the block before it, so removing never loses writing. An empty marker stays in the draft so it can be typed into, and is dropped on save like any block with no text (see normalizeContent). A locked day shows markers but offers no Add or Remove. The logic is in packages/core (minuteMarkers.ts), the screen only calls it.

## D-019: Drafts live in AsyncStorage, one per user and day, and Firestore keeps its own offline cache

While a day is being written, the text is saved to the device's AsyncStorage under `draft:v1:{uid}:{dayId}`, at most 3 seconds after typing starts, and also when the app goes to the background or the screen closes. The key includes the uid so two accounts on one device never share a draft. The stored value is checked with zod when read; data that is not valid JSON or has the wrong shape or version is treated as no draft instead of crashing the screen. A day with no text has no stored draft, so clearing the text removes it. A failed read does not block writing (the screen starts empty and shows the warning). A failed write keeps the text on screen, shows a warning, and is retried on the next edit, on going to the background, and on leaving. Writes go through a queue so an older write can never land after a newer one. The writer is not shown until the stored draft has been read, so a stored draft is never overwritten by an empty one. Drafts are separate from revisions: nothing is sent to Firestore here, and committing a draft as a revision and clearing it is commit 22. Offline sync of saved data needs no new code: firebase.ts already turns on Firestore's persistent local cache (section 6), which queues writes made offline and sends them when the connection returns. The draft logic is in the app (draftStore.ts, useDayDraft.ts) because it depends on AsyncStorage; the storage is passed in so tests use an in-memory fake.

## D-020: Revisions are saved from the Day screen and the sitting is closed when the screen closes

Pressing Save, or leaving the Day screen, runs planSave from packages/core against the passes the screen listens to (users/{uid}/days/{dayId}/revisions, ordered by the field n because document ids are text and 10 sorts before 2). The revision and the day document (latestRevision, wordCount, updatedAt, firstWrittenAt) are written in one batch, so the calendar never shows a day without its text. firstWrittenAt is taken from revision 1, so later passes keep it. A sitting lasts until 30 minutes after the last save (the updatedAt of the day document) or until the screen closes. Leaving the screen saves any unsaved text and then sets closedAt on the open revision, which makes it immutable under the rules. If a sitting ran out without the screen closing (for example the app was killed), the next save closes the old revision at its last save time in the same batch, so no revision stays open forever. A save made offline is visible at once through the listener, marked as pending, and syncs later. The draft on the device is removed only after the server confirms the save, so a refused save loses nothing, and the Save button stays usable while an earlier save waits to sync. The draft starts from the latest saved pass when the device has no draft; a stored draft wins over the saved pass. Known limit: if one day is edited on two devices, an older stored draft could be saved as a newer pass. Both passes stay in the history and nothing is deleted. The revision toggle (Latest, 1st, 2nd and so on) is shown only when a day has two or more passes. Latest is the pass that can be edited; numbered passes are read-only. Highlighting additions between passes is commit 23.

## D-021: Highlight additions shows the saved pass read-only, compared with the pass before it

The Highlight additions switch appears under the revision toggle when a day has two or more passes. When it is on, the selected pass (Latest included) is shown as a read-only list of the parts of the day that have text, and the words that were not in the previous pass are marked. The comparison is markAdditions from packages/core: case and surrounding punctuation are ignored, and words are matched as a multiset, so a word repeated more often than before counts as added. Added words are bold on a coloured background, and a summary line gives the count, so the mark does not depend on colour alone. The first pass has nothing earlier, so the switch is off and disabled for it. The highlighted view cannot be typed into, because a text field cannot show inline marks. For Latest it shows the saved pass, not unsaved draft text, and a hint says to switch off to keep writing; the draft is kept untouched meanwhile. The switch resets when another day is opened.

## D-022: Tags and categories have their own screens, and the default categories are seeded with fixed ids

The Tags area has four routes: /tags (list with search and category filter), /tags/new, /tags/[tagId] (edit and delete; the mention history is added by commit 26) and /tags/categories. Home gets a plain Tags link until commit 38 adds the full navigation. People, Places and Numbers have the fixed ids `people`, `places` and `numbers` and are written the first time the categories load if any is missing, so two devices seeding at once write the same documents. They cannot be renamed or deleted. Custom categories can be created, renamed and deleted. A custom category can only be deleted while no tag uses it, and the message says how many tags do; moving the tags automatically was rejected as the more complex choice. A tag name must be unique inside its category, ignoring case, and the same name may exist in two categories. Limits: name 60 characters, note 500, at most 10 aliases of 60 characters each. Aliases are split on commas or new lines, repeats are dropped ignoring case, and an alias equal to the name is dropped. An empty note is stored as null. Search matches the name or any alias, ignoring case, and the list is sorted by name. All of these checks are in packages/core (tags.ts). `createdAt` is stored as epoch milliseconds, like the revisions. The screens do not wait for writes: Firestore shows the change at once and confirms it later, and a write made offline stays queued. A write the server refuses is shown as a banner on the Tags and Categories screens. Delete asks for confirmation inside the screen instead of using Alert.alert, because Alert does nothing in the web build that the Windows app is made from. Deleting a tag removes only the tag document. Revisions are immutable, so old entries keep their `{{tag:ID}}` tokens, and commit 25 must define the token so that the name stays readable as plain text once the tag is gone (section 5.4).

## D-023: Mentions are typed as `@Name`, stored as tokens with the name inside, and inserted with spacing

A text field cannot show a chip inside its text, so the writer shows a mention as `@Name` and stores it as `{{tag:ID|Name}}`; the name is URL-encoded so a token never holds spaces, and it is what keeps an old entry readable after the tag is deleted (section 5.4, D-022). The conversion in both directions lives in packages/core (mentions.ts), so mobile and desktop behave the same. A mention shows the tag's current name, so a renamed tag updates everywhere while the stored name stays as it was. Typed text becomes a mention only when it is `@` plus exactly a known tag name (case sensitive) that does not touch a letter or digit on either side, so `@Ravindu` is not the tag Ravi. Editing the name of a mention turns it back into plain text. Inserting a mention adds a space after it, and before it when a letter or digit precedes, because otherwise the next keystroke would break it. Typing `@` lists up to 8 matching tags (name or alias) grouped by category, with a Create new tag row. The Insert tag button opens a searchable picker of all tags, and Save as tag turns the selected text into a tag; both reuse the tag form. A new tag is stored without waiting (its id exists at once), so the mention is inserted immediately and a refused write is shown as a banner on the Day screen. The collapsed row preview shows `@Name` and is cut after the conversion. The highlighted view shows names too; read-only views show mentions but offer no picker.

## D-024: The day document carries the tag ids of its latest pass, and the tag screen lists days from it

To list the days that mention a tag without reading every revision, saveDayContent also writes `mentions` (the tag ids of the latest pass, in order of first appearance) on the day document, in the same batch as the revision. The tag screen (/tags/[tagId]) queries users/{uid}/days with `mentions array-contains tagId`, which needs no composite index and no change to the rules, and mentionedDays in packages/core sorts the result newest first. Each row shows the date and the word count of the day and opens that day. The mention history is shown above the edit form. Because the field follows the latest pass, a tag removed from the text in a later pass no longer lists that day, while the older pass still holds the mention. Known limit: days saved before this commit have no `mentions` and are listed only after they are saved again; no backfill is run because the app has no released data yet. Movies and books join the same list with the library in commit 27, which stores `mentions` on the library item in the same way.

## D-025: Movies and books are pages with the same revision rules as days, without the 9 PM lock

A movie or book is one document at users/{uid}/library/{itemId} with a title, an optional date, and a page of plain text. The page is saved as numbered revisions in users/{uid}/library/{itemId}/revisions, using the same planSave, buildRevision and sitting rules as days (D-020), so a page can be written at any hour. The conversion between a page and the day shapes is in packages/core (library.ts: libraryContent, toDayRevision, toLibraryRevision), so no second copy of the revision logic exists. The item document carries the summary of its latest pass (text, latestRevision, wordCount, updatedAt, mentions), written in the same batch as the revision. updatedAt means the last time the text was saved (or when the item was added, until the first save), so editing the title or the date does not affect sitting detection. The tag screen queries the item documents with `mentions array-contains tagId` and shows the movies and books below the days, dated items first (D-024). The rules mirror days without the lock: a revision can be created by its owner, updated only while it is open (no closedAt), and deleted only while open or during account deletion; reading is always allowed for the owner. Left out on purpose: deleting an item, because deleting would orphan its immutable revisions and the documentation does not ask for it, and Highlight additions on pages, because the documentation specifies it only for days. Known limit: items saved before a tag was created have no way to list it until they are saved again, as for days.

## D-026: The recall score is a mean of per-day scores, computed from the passes of each day

The score follows section 8.1 and lives in packages/core (score.ts). It takes the days with their passes and today's id, so it needs no clock and no Firestore. Each written day (one with a revision 1, on or before today) earns up to 30 Detail, 20 Coverage, 20 Precision, 15 Later recall and 15 Consistency. The displayed score is the mean of the last 14 written days, rounded to a whole number, and is null until a day is written. Choices the documentation left open: Detail is the word count of revision 1 divided by the user's average revision 1 word count over the 30 days ending with that day (the day included, so the average is never zero when text exists), and the points are 30 times min(ratio, 1.5) divided by 1.5, so an average day earns 20 and 1.5 times the average earns all 30. Coverage counts hours that have non-blank text in revision 1; free notes do not count because they have no hour. Precision counts minute markers with non-blank text plus the distinct tags mentioned in revision 1. Later recall adds the addedWordCount of every pass after the first, but only while the day is older than one day as seen from today (a day that is two or more days old), so a second pass on the same evening or the next day does not count as remembering later. Because it depends on today, a day's Later recall grows into the score as it ages. Consistency is the days written in the 14 days ending with that day, out of 14, so a new user starts with a low value and it rises as days are written. The weekly change is the score now minus the score computed as of 7 days ago from only the days up to then, and is null when either score is missing. The caller decides when to store the result in users/{uid}/stats (commit 31 shows it, commit 32 puts it in the home header). The info sheet that says the score is a motivation tool and not a medical measure belongs to the Insights screen.

## D-027: The streak is computed from the days that counted, and a freeze is spent per missed day

The streak lives in packages/core (streak.ts) and follows section 8.2. A day counts when its first pass was saved on the same local calendar day, at 21:00 or later, with at least 20 words (countsTowardStreak, using the user's stored offset). A first pass saved after midnight belongs to the earlier day but does not count, and later passes never count. computeStreak takes the list of days that counted and today's id and returns currentStreak, longestStreak, lastStreakDay and freezeCount, so it is deterministic and can be recomputed at any time instead of being mutated; the caller decides when to store the result in users/{uid}/stats. Days after today and repeated days are ignored. Today is never treated as missed, because it can be written until midnight, so a streak that ended yesterday still shows until today is over. Each missed day spends one banked freeze and leaves the streak as it was; when a missed day finds no freeze left, the streak goes to 0. Freezes are spent one per day, so three missed days with two freezes spend both and then break the streak; keeping the freezes for a gap that cannot be saved was rejected because the documentation says a freeze is spent when a day is missed. A day covered by a freeze is not counted, so it does not add to the streak. A freeze is earned each time the streak reaches a multiple of 7, up to 2 banked, so it is earned again after a reset and after a freeze was spent. Milestones are 3, 7, 14, 30, 60, 100 and 365: newMilestone reports the highest one crossed by a step and nextMilestone the next one to reach. Known limit for commit 32: a day's metadata holds firstWrittenAt (the time of revision 1) but the word count of the latest pass, not of revision 1, so the app must read revision 1 of a day to know whether it had 20 words; a way to store that is to be decided when the streak is first stored. daysBetween was added to time.ts and is shared with score.ts.

## D-028: Motivational messages are a priority-ordered rules engine over a context the caller builds

The engine lives in packages/core (messages.ts) and follows section 8.3. It is a pure function of a MessageContext: the streak, the streak before the latest save, the score and its weekly change, the number of written days, today's words against the user's 30-day average, the latest pass on an older day, the missed days before the latest activity, and the first-time flags. It reads no clock and no Firestore, and it keeps no state, so every number in a message comes from the journal and the caller (commit 31 for the Insights screen, commit 32 for the home header) decides when to build the context and which message id was shown last. There are 18 triggers and 68 templates (the documentation asks for at least 60), and each trigger has at least two variants. The highest-priority trigger that applies decides the message, and the tip trigger always applies, so there is always a message. The variant is chosen from a caller-supplied seed and is never the id shown last, so the same sentence does not appear twice in a row. Choices the documentation left open: a rise of 5 points or more counts as a rise; a return after a break means 3 or more missed days; 'nearly there' means 3 days or fewer to the next milestone; the above-average message needs at least 3 written days and more words than the rounded average; the freeze message appears at every multiple of 7 below the milestone messages; a day is referred to as yesterday, by weekday within the last week, and by date after that. The total of written days is celebrated at 10, 25, 50, 100, 200 and 365. Messages are encouraging and factual and never blame; a return after a break is welcomed without counting what was missed. The optional AI upgrade in section 8.3 is not implemented.

## D-029: The Insights screen reads the 80 most recent written days in full and older days only for the streak

The Insights screen (commit 31) works everything out on the device from the user's own passes, through buildInsights in packages/core (insights.ts), and stores nothing; putting the results in users/{uid}/stats is left to commit 32 if the home header needs it. loadInsightsInput reads the day metadata (all days up to today, newest first), then every pass of the 80 most recent written days, because the score looks at 14 written days and each of them at up to 30 days before it, and the oldest trend point is 29 days back. Older days are read only to learn whether they counted toward the streak: the day metadata holds firstWrittenAt, which rules most days out, and for a day with a single pass also the word count; only a day with later passes needs revision 1 itself, because the metadata word count belongs to the latest pass. This settles the known limit left open in D-027 without adding a field. The trend is the score as of each of the last 30 days, today included, oldest first. Just saved means the latest pass over all days was created today (in the user's offset); only then does the message context carry the things that depend on a save (a milestone just reached, a later pass on an older day, a first tag or minute marker, a welcome back after a break), so an old celebration does not stay on screen for weeks. A pass is dated by when its sitting began. A first tag or minute marker is a first only when no other pass in the read days uses it, and a first library item means the library holds exactly one item and it was saved today. The screen shows one message (the seed moves on with the date, so the same trigger gives a different variant the next day), the score with its change against a week ago and an info text saying it is a motivation tool and not a medical measure, the streak with the next milestone and a note on freezes, and the trend as 30 bars with a spoken summary for screen readers. The last numbers stay on screen when a refresh fails, with a Try again button. Journal text is read on the device and goes nowhere else.

## D-030: The home header is a tappable bar that reads the same numbers as Insights

The top bar of the home screen (StatsBar) shows the current streak and the latest recall score and opens the Insights screen when pressed. It reuses useInsights, so the numbers are exactly those on the Insights screen and nothing is stored in users/{uid}/stats; the cost is one read of the 80 most recent days when Home opens (Firestore's local cache serves it offline), which was judged simpler and safer than keeping a second copy of the numbers in step with every save. Home stays mounted underneath the Day screen, so the numbers are read again each time Home regains focus after the first; the last numbers stay visible while that read runs. Before the first read, or when it failed with nothing to show, the bar shows a dash for both values instead of a zero, so a wrong number is never shown, and its spoken label says that it is loading or could not be refreshed. A journal with no written day shows a streak of 0 days and a dash for the score. The bar is not the full navigation, which arrives in commit 38, so the Tags, Library and Insights links stay on Home until then.

## D-031: Lessons are bundled as TypeScript strings in a small markdown subset

The seven required lessons live in packages/core/src/tutorials/lessons.ts as plain strings, not as .md files, because core is consumed as TypeScript source (D-003) and a markdown file would need a loader in Metro, Jest and Electron. Each lesson has an id, a title, a one-sentence summary, a reading time and a body. The ids are kept in the user's progress (users/{uid}/progress/tutorials), so an id is never renamed. The body uses only headings, paragraphs and bullet lists, so every screen draws it the same way with parseLesson and no markdown library; a test fails if a lesson uses anything else (bold, links, code, tables, images). Every lesson ends with a Try it tonight section of plain paragraphs, which exerciseOf returns, so the Learn screen can show the exercise under a button that opens today's page (commit 34). The memory palace lesson uses the user's own home, as the documentation asks. The progress helpers cleanCompleted, toggleCompleted, learnProgress and nextLesson work on the stored list of finished ids: unknown ids (a lesson removed in a later version), repeats and values of the wrong type are dropped, and the order is the teaching order, so a damaged document cannot break the screen. Wording choices: the lessons make no medical claims and describe spaced gaps as a common pattern, not a rule, and the first lesson repeats that the recall score is a motivation tool, not a medical measure (D-026).

## D-032: Learn progress is one document updated with array union, and the lessons never wait for it

The Learn screens (commit 34) draw the lessons straight from the bundle, so they work offline and show at once; only the Done ticks wait for users/{uid}/progress/tutorials. Marking a lesson done writes { completed: arrayUnion(id) } with merge, and marking it not done writes arrayRemove(id), instead of writing the whole list, so two devices that mark different lessons never overwrite each other and an offline write waits in Firestore's queue. The screen does not wait for the write; a refused write shows a dismissible banner on the lesson screen (Your progress could not be saved). An unknown lesson id writes nothing. What is read is passed through cleanCompleted (D-031), so a damaged document reads as less progress, never as an error. A missing document reads as no progress. If the progress cannot be read, the list still opens and a short note says the progress could not be loaded. The routes are /learn and /learn/[lessonId], flat like the other screens until the full navigation arrives in commit 38, so Home gets a plain Learn link next to Tags, Library and Insights. The Try it tonight button, labelled Open today's page, sits at the end of the lesson text because that section is always last, and opens /day/{today}; the Day screen decides whether today is writable yet. The existing rule for progress/{documentId} already allows only the owner, and rules.test.ts already proves another user cannot read it, so no rules change was needed.

## D-033: The daily reminder follows one rule set on phones and desktop

Both reminders (commits 35 and 36) show the same words at 21:00 local time, taken from packages/core/src/reminder.ts (REMINDER_TITLE, REMINDER_BODY, REMINDER_HOUR), and both follow reminderAction: with the reminder off nothing is scheduled and the person is never asked; permission is asked for only while it is undetermined, which is the first launch after sign-in, and a refusal is not asked again; with permission the reminder is scheduled again, which also repairs a missing or stale schedule. The Settings toggle does not exist yet, so useReminder and useDesktopReminder take an enabled argument that defaults to true; the Settings commit passes the real value. On phones (commit 35) expo-notifications schedules a daily trigger with a fixed identifier, so scheduling again replaces the old one rather than adding a second; it is scheduled again after sign-in, when the toggle changes, and when the device offset from UTC changes, which is noticed when the app returns to the foreground (so a new time zone or a daylight saving change is followed). A tap on the notification opens /day/{today}, once per tap.

On Windows (commit 36) the system cannot be given a daily repeat, so the Electron main process looks at the clock every 30 seconds (reminderScheduler.ts) and asks reminderDue in packages/core whether a reminder is owed. The rule lives in core so it is tested with explicit offsets like the other time rules: one reminder per local day, from 21:00 until REMINDER_LATE_GRACE_MS (one hour) later, so a computer that wakes from sleep at 21:20 still reminds and one that wakes at midnight does not. The main process also looks at the clock when the computer resumes, because timers do not run during sleep, and it reads the device offset on every check, so a new time zone is followed. Switching the reminder on after 21:00 counts that evening as already reminded, so signing in at 21:30 does not produce a notification at once; switching it off and on again after 21:00 does the same. The window tells the main process whether a reminder is wanted through the preload bridge (setReminderEnabled with signed in and the toggle), and the main process starts with it off, so a signed-out app never reminds. Clicking the notification shows the window and sends reminder:open-today, and the app opens /day/{today} only while signed in; the preload hands the page nothing but the callback, never the IPC event. Closing the window hides it to the system tray instead of quitting, as the documentation asks, so the reminder keeps working; the tray icon reopens the window and its menu has Quit, a second launch shows the existing window, and the app really quits on Quit, on logoff or shutdown (session-end) and on any app.quit. The app user model id is set only in the packaged app, because in development a made-up id with no Start menu shortcut makes Windows show nothing.

Known limits: no reminder is shown while the app is not running (after Quit from the tray, or with the computer off); a click that reached a window that had to be created again while the app was still loading would not open today, which cannot happen in normal use because the window is hidden, not destroyed; and the tray icons assets/tray.png and assets/tray@2x.png are placeholders drawn by scripts/make-tray-icons.mjs, to be replaced with real artwork.

## D-034: Settings save one field at a time; export and account deletion run on the device

The Settings screen (commit 37) is the route /settings, opened from a Settings link on Home, which is also where Sign out moved to. The profile (name and email) is read from the signed-in account and cannot be edited. The reminder toggle and the theme each write a single field (settings.reminderEnabled, settings.theme, with updateDoc), so two devices that change different settings do not overwrite each other and a change made offline waits in Firestore's queue; a refused write shows a short message. readSettings in packages/core falls back to the default for each setting on its own, so a half-written document never turns the reminder off. The root layout passes the toggle to useReminder and useDesktopReminder (D-033) through reminderWanted: off while the stored setting is still being read, so someone who turned the reminder off is not reminded for a moment at start-up; the stored value once it is read; and on if it cannot be read, which is the default in section 5.8. The theme is saved but not applied yet, because the dark theme and the responsive layout are commit 38. The 21:00 unlock time is not a setting.

Export all data (section 5.9) reads the profile, every day and library page with all of its revisions, the tags, the categories and the tutorial progress. buildExport in core turns them into plain JSON in a fixed order (days by date, revisions by number, timestamps as ISO 8601 strings in UTC) in a file labelled memory-journal-export, version 1, so the same data always gives the same file apart from the export time. A failed read rejects, so a partial file is never handed over as complete. Delivery depends on the platform: the web build inside the Windows app saves a .json file through the browser, and phones open the system share sheet with the JSON as text, because expo-file-system and expo-sharing are not dependencies of the app. A real file attachment can replace the share sheet later.

Delete account and all data runs on the device, because v1 has no Cloud Functions (D-009). The person confirms twice: a plain warning that says what is lost and that it cannot be undone, then typing the word DELETE (case and spaces do not matter). deleteAccount then asks for a Google sign-in again, because Firebase wants a recent sign-in before it deletes an account; choosing a different Google account fails, and cancelling changes nothing. It then sets deletionRequestedAt on users/{uid}, which needs a connection and gives up with a clear message after 30 seconds. After that it deletes the revisions, then the days and library pages, then the tags, categories and tutorial progress, in batches of 400, and the user document last, because the rules read it to allow the deletion of closed revisions; if it went first, leftover revisions could never be removed. The drafts held on this device are cleared, the phone reminder is cancelled, and the Firebase account is deleted last, which signs the app out. Running it again after a failure continues where it stopped, because a user document that is already gone is not an error. While it runs, syncUserProfile writes nothing, so the profile sync cannot make a new user document in the middle of the deletion. The rules needed no change (D-009).

Known limits: deleting needs an internet connection; if removing the Firebase account fails after the data is gone, the person stays signed in with an empty account and can run the deletion again; and on Android the share sheet can fail for a very large journal, which a file attachment would fix.

## D-036: Text colours are tested against WCAG AA; the side navigation is keyboard-driven (Alt+1 to Alt+6)

Commit 39 fixes the accessibility problems that D-035 listed as unreviewed. Colours: contrast.ts computes the WCAG contrast ratio, and contrast.test.ts checks every text pair the screens draw (text, muted, accent and danger on the page and on the surface, and the text on an accent fill) in both palettes against 4.5:1, the AA level for normal text. The test failed for four dark pairs, so the dark palette changed: muted #a1a1a6, accent #4da3ff, danger #ff6961, and the text on an accent fill is now black (onAccent #000000), because white on a blue light enough to read on dark surfaces is below 4.5:1. The light palette already passed. Changing a palette colour now fails a test if it breaks contrast.

The Day screen files (calendar, day header, writer, save bar, revision toggle, draft status, highlight switch and highlighted view), the Day route's error line and the sign-in screen still drew with their own fixed colours, several of which were below 4.5:1 (for example grey #8e8e93 on white in the calendar, and white on #0a84ff in the save bar and revision toggle). They now read the theme palette. Three fills stay local because they are tints behind normal text, not text colours: the calendar's written-day fill, the highlight fill for added words, and the Day banner. The sign-in button had no border colour, so its border was black on the dark page; it now uses the accent. Future days in the calendar keep a faint colour because they are disabled, which WCAG leaves out of the contrast rule.

Keyboard and screen reader: the side navigation is now a navigation landmark ("Main") of links, replacing the menu and menuitem roles, which tell a screen reader to expect arrow-key menu behaviour that was never built. The narrow-screen link list on Home is a landmark too ("Sections"). Alt+1 to Alt+6 open Home, Tags, Library, Insights, Learn and Settings on the web build and in the Windows app, while signed in. shortcutIndex (tested) uses the physical key, so it works on any keyboard layout; it needs Alt and no other modifier, and ignores the numpad because Alt plus numpad digits types characters on Windows. On the web build a focus ring (2 px, the accent colour, :focus-visible only) is added through a style element, because the text fields of the web build have their outline removed. Escape closes the add-minute form and the tag search. The save line under the Save button is a polite live region, so a screen reader announces "All changes saved". Known limits: the shortcuts, the focus ring and the roles were checked by tests of the pure parts, the type checker and lint, but nobody has used the app with a screen reader (TalkBack, Narrator, NVDA) or tabbed through it in the Windows app, so the tab order is as the screens are laid out and has not been reviewed; the banner, highlight and calendar fills are not part of the contrast test; Alt+number can be taken by a browser or the system on some platforms, in which case that shortcut does nothing; the Android navigation bar still follows the system, as in D-035; and there is no skip-to-content link.

## D-040: Holidays come from the static JSON files of srilanka-holidays, not from its API

The request was to use the public API of `Dilshan-H/srilanka-holidays`. Its README says that since v2.0.0 every API call needs an `X-API-Key` header and that keys are issued to one developer on request. A key inside an app that other people install is public, ties every user to one developer's quota and can be revoked for all of them. The same project publishes the data as static files (`json/<year>.json`), which need no key and are MIT licensed. The app therefore downloads `https://raw.githubusercontent.com/Dilshan-H/srilanka-holidays/main/json/<year>.json`. Only `start` (date) and `summary` (name) are used. If the maintainer issues a key later, the source is one constant in `holidayService.ts`.

Known limit: the page that lists the other fields of the file could not be opened while this was planned (the site refused automated access), so only `start` and `summary` are read and everything else in an entry is ignored. If the shape differs, the parser skips the entry and the calendar shows no holiday instead of failing.

## D-043: A page is stored in `freeNotes` with empty `blocks`

The Day page is one string, so a pass saved by v0.2.4 puts the whole page in `freeNotes` and saves `blocks` as an empty list. This avoids a schema change and a Firestore rules change. `normalizeContent` sorts blocks into time order, which would reorder what the person wrote, so new passes do not use blocks. `packages/core/src/dayPage.ts` reads and writes the page (`pageOf`, `contentFromPage`, `timeBlocksOf` and the time line and cursor helpers).

Known limit: an older version of the app that reads such a pass shows it as plain free text.

## D-044: Time lines are lines of the form `⏱ HH` or `⏱ HH:MM`

A line is a time only when the whole line is exactly the symbol, a space and two digits for the hour, with optional `:` and two digits for the minutes. The symbol inside a sentence stays plain text. Add time puts the line on its own line at the cursor and moves the cursor to an identical line that already exists instead of adding a second one. Two identical lines typed by hand are both kept.

## D-045: The score reads time lines, and a page with none is valid

Detail uses the word count of revision 1 without time lines. Coverage counts the distinct hours with a time line followed by non-blank text, and Precision counts the time lines with minutes plus the distinct tags. A page with no time lines scores 0 for Coverage and for the minute part of Precision on that day, which is the cost of not marking times. Later recall, Consistency and the streak are unchanged, and the 20-word rule ignores time lines.

## D-046: Older days convert on first edit and SaveBar stays

Existing days and passes are never rewritten. View mode shows them through `pageOf` (Free Notes first, then the rows in time order). The Pencil on a legacy Latest pass starts the editor with `pageOf(content)`, and saving creates the next pass, or updates the open one, in the new shape. Section 18.8 listed `SaveBar` for removal, but the Library item screen still uses it, so only `DayWriter`, `HighlightedDay`, the old Day tests and `minuteMarkers.ts` were removed (step 6).

## D-047: Nothing moves, scales or shakes as an animation

From v0.2.5 no element changes its position, size or angle as an animation. Only opacity, colour, drawn strokes, filled bars and counting numbers animate. Stack screens, sheets and dialogs fade over 150 ms. The shared spring and the stagger-by-translation helpers are deleted, and the check in section 4.4 of the v0.2.5 plan keeps it that way. The names PressableScale, FadeUp and Reflow are kept so call sites do not change.
